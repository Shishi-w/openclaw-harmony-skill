# 团队分工

> 本文档定义小组的组织结构、分组职责、每位成员的角色与工作边界。
> 本仓库为**公开**仓库，文中仅登记姓名/学号/分工，不登记任何隐私联系方式（联系方式走群聊/私聊）。
> **维护人：组长**。成员名字由组长在 `member-roster.md` 中登记，此处按下组 + 角色描述，避免频繁改人名。

## 一、总体结构与人数配额（约 22 人）

```
                ┌──────────────┐
                │  组长(1人)    │  统筹、对外、最终决策
                └──────┬───────┘
        ┌──────────────┼───────────────────┐
        ▼              ▼                   ▼
   ┌─────────┐   ┌──────────┐   ┌──────────────┐
   │ 方向A    │   │ 方向B     │   │ 公共支撑小组   │
   │ 传统移植  │   │ Skill VM │   │ (环境/文献/记录)│
   │ ~8人    │   │ ~8人     │   │ ~6人          │
   └─────────┘   └──────────┘   └──────────────┘
```

> 人数为建议配额，可按实际报名灵活调整（尤其支撑组可兼职）。所有组员在**每个大阶段**都承担一定的文献阅读任务，不设"只写代码"或"只看论文"的成员。

## 二、方向 A：逐 Skill 移植组（约 8 人）

**目标**：把 OpenClaw 的 Skill 逐个分析与改写，适配鸿蒙大模型运行环境，最终沉淀一套"移植清单/Skill 移植档案"。

| 子组 | 建议人数 | 职责 | 交付物 |
| --- | --- | --- | --- |
| A1 基础系统类 | 3 | 文件读写、命令执行、文本/数据处理等系统级 Skill 的移植 | 移植后的 Skill 目录 + 移植档案 |
| A2 网络与应用类 | 3 | 浏览器、搜索、网页抓取、HTTP API 类 Skill 的移植与鸿蒙网络能力对接 | 同上 |
| A3 办公/工具链类 | 2 | 文档、图像、表格等业务类 Skill 移植，分析其外部依赖替代方案 | 同上 |
| A4 （兼职）移植工具链 | 1 | 把"逐一手工移植"沉淀成半自动化脚本/清单（为方向B提供输入） | 移植分析脚本 + 分类清单 |

**工作范式**：每个 Skill 用 `templates/skill-port-template.md` 记录一次完整移植（原始分析 → 依赖清单 → 重写方案 → 测试结果）。

## 三、方向 B：Skill VM 研究组（约 8 人）

**目标**：设计并实现"Skill 与 OS 解耦"的抽象层（Skill VM：中间表示 + 运行时 + 宿主适配器），一次编写、多端运行，产出创新性原型与论文素材。

| 子组 | 建议人数 | 职责 | 交付物 |
| --- | --- | --- | --- |
| B1 规范与 IR 设计 | 2-3 | 研究 AgentSkills 规范与 OpenClaw 加载/门控机制，设计 Skill 中间表示（IR/Schema） | IR 规范文档 + Schema 定义 |
| B2 运行时与沙箱 | 3 | 实现 Skill VM 执行器、配置解析、门控模拟、上下文注入、权限沙箱 | 可运行的最小 VM 原型 |
| B3 宿主适配层（HarmonyOS） | 2-3 | 定义宿主抽象接口（工具调用、环境探测、文件/网络），实现鸿蒙侧适配器 | 鸿蒙适配器代码 + 可行性报告 |

## 四、公共支撑小组（约 6 人，鼓励兼职）

| 子组 | 建议人数 | 职责 | 交付物 |
| --- | --- | --- | --- |
| C1 环境与 CI | 2 | 维护环境搭建文档、解决成员环境问题、搭建 GitHub Actions 基础流水线、脚本审查 | 可用的 CI + 环境答疑记录 |
| C2 文献与调研 | 2 | 论文检索方法、领域综述牵头、组织每周论文分享、维护综述文档 | 文献综述 + 周分享记录 |
| C3 文档与记录 | 2 | 统一文档规范、会议纪要归档、模板维护、README 维护、版本发布说明 | 归档齐全的文档库 |

## 五、角色与职责总览（个人维度的建议分工）

组长可按下面的"角色筐"为每位成员打勾分配（一人可多筐，但主责唯一）：

| 角色 | 说明 | 建议人数 |
| --- | --- | --- |
| 组长 | 统筹规划、对外联络、最终决策、组织例会 | 1 |
| 方向A负责人 | 拆分 A 组任务、跟进进度、汇总移植档案 | 1 |
| 方向B负责人 | 拆分 B 组任务、跟进进度、把握 VM 架构方向 | 1 |
| 支撑组协调 | 汇总环境问题、文档、文献三条线的进度 | 1 |
| 各组组员 | 按组职责执行具体任务（详见上方分组） | 其余 |
| 例会轮值记录 | 每周 1 人轮值写会议纪要（可多排） | 轮值 |

## 六、新成员 Onboarding 清单（第一周必做）

每位新成员加入后，一周内按顺序完成：

- [ ] 注册 GitHub 账号，把用户名发给组长，接受仓库邀请
- [ ] 通读 `README.md`，clone 仓库到本机
- [ ] 完成 `docs/03-environment/git-intro.md`（新手对照一步步来）
- [ ] 完成 `docs/03-environment/openclaw-setup.md` 中的基础安装，确保 `openclaw` 命令可用
- [ ] 通读 `docs/01-overview/research-goals.md` 和所属方向的 `docs/04-methodology/` 文档
- [ ] 在 `member-roster.md` 填写自己的姓名/学号/偏好方向
- [ ] 在例会上认领第一条任务，工单在 `docs/05-protocols/task-board.md` 或 GitHub Projects

## 七、协作红线

1. **认证即认领**：不在线安排、群里 A 一下的任务优先级最低；正式任务一律记录在任务看板。
2. **文档先行**：任何代码/方案先有对应文档或 PR 描述，防止"人走了、知识也没了"。
3. **公开仓库纪律**：不提交任何私密信息（API Key、账号密码、校园内部资料、未发表成果）。
4. **命名规范**：目录、文件、分支、Skill 名称按 `docs/05-protocols/git-workflow.md` 约定。
