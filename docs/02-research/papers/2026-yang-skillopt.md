# SkillOpt 论文阅读报告

Yifan Yang, Ziyang Gong, Weiquan Huang, et al. *SkillOpt: Executive Strategy for Self-Evolving Agent Skills*. arXiv:2605.23904v2, 2026. [论文版本](https://arxiv.org/abs/2605.23904v2)；[官方代码](https://github.com/microsoft/SkillOpt)。

## 1. S：总览

SkillOpt 把 Skill 文档当作可以离线训练、验证和版本化的外部知识，核心方法是根据真实执行失败改写技能，再用独立任务决定改动是否成立。这可作为移植后的行为适配与评测方法。

## 2. Q：阅读问题

**RQ1：原有 Skill 更换模型或执行环境后，哪些流程知识还能复用，效果会怎样变化？**
**RQ2：移植后的 Skill 表现不佳时，能否根据执行反馈自动修正，减少逐个手工调试的工作？**
**RQ3：如何评判skill移植的成功度？**

## 3. R（Read）

RQ1：原有 Skill 更换模型或执行环境后，哪些还能复用，效果会怎样变化？

跨模型：表格操作 Skill 和数学解题 Skill 已验证可复用

表4(a)（p.9）将 GPT-5.4 上优化得到的两份 Skill，直接用于 GPT-5.4-mini 和 GPT-5.4-nano，目标端不再优化 Skill。

| 复用的 Skill | 模型迁移方向 | 目标模型无 Skill | 复用后成绩 | 提升（百分点） |
| --- | --- | ---: | ---: | ---: |
| SpreadsheetBench 表格操作 Skill | GPT-5.4 → GPT-5.4-mini | 36.1 | 45.5 | +9.4 |
| SpreadsheetBench 表格操作 Skill | GPT-5.4 → GPT-5.4-nano | 23.5 | 26.5 | +3.0 |
| LiveMath 数学解题 Skill | GPT-5.4 → GPT-5.4-mini | 14.7 | 19.2 | +4.5 |
| LiveMath 数学解题 Skill | GPT-5.4 → GPT-5.4-nano | 23.2 | 28.8 | +5.6 |

四组迁移均提高了目标模型的成绩，因此这两份 Skill 在上述模型之间具有直接复用价值。复用后的效果与目标模型上重新优化的效果也有差别：例如 nano 的表格成绩为26.5，低于直接优化的42.5；nano 的数学成绩为28.8，则略高于直接优化的27.2。

跨 harness：表格操作 Skill 和数学解题 Skill 已验证可在 Codex 与 Claude Code 间复用

表4(b)固定执行模型为 GPT-5.5，将一侧优化得到的 Skill 直接放入另一侧使用。这里改变的是执行框架（harness），目标端同样不重新优化 Skill。

| 复用的 Skill | harness 迁移方向 | 目标框架无 Skill | 复用后成绩 | 提升（百分点） |
| --- | --- | ---: | ---: | ---: |
| SpreadsheetBench 表格操作 Skill | Codex → Claude Code | 22.1 | 81.8 | +59.7 |
| SpreadsheetBench 表格操作 Skill | Claude Code → Codex | 27.5 | 71.1 | +43.6 |
| LiveMath 数学解题 Skill | Codex → Claude Code | 40.8 | 42.4 | +1.6 |
| LiveMath 数学解题 Skill | Claude Code → Codex | 35.2 | 48.0 | +12.8 |

这两类 Skill 在两个方向上都取得正收益，其中表格操作 Skill 的收益更大。Codex → Claude Code 的表格成绩81.8还略高于在 Claude Code 中直接优化的80.4；反方向的71.1低于在 Codex 中直接优化的85.0。数学 Skill 的两个迁移方向也有明显差异。

这一层的结论是：**论文验证了两类 Skill 在 Codex 与 Claude Code 之间可直接复用，表格操作 Skill 尤其显示出较强的跨框架复用效果。** 这些结果对应指定任务、模型和框架组合，论文没有对其余主基准逐一提供跨 harness 迁移结果。

跨 OS：论文未验证哪些 Skill 可以复用

论文没有报告同一份 Skill 在不同操作系统之间迁移的对照实验，也没有 OpenClaw → HarmonyOS 的迁移实验。因此，这一层尚无已验证的 Skill 清单。

### 3.2 RQ2：移植后的 Skill 表现不佳时，能否根据执行反馈自动修正，减少逐个手工调试的工作？

**论文提供了一套根据执行反馈自动修改 Skill 的方法，可以作为目标环境中技能调试的参考。** 它把“运行任务”和“修改技能”分成两个角色：执行模型按照当前 Skill 做任务，优化器模型读取执行记录并提出修改；两者可以使用同一种模型，也可以使用不同模型。执行模型的权重在整个过程中保持不变。

具体过程见§3.2–§3.6和算法1：

1. **先运行一批任务，收集问题发生的过程。** 记录包括工具调用、观察结果、命令输出、最终答案和评分反馈。例如，可以据此发现模型漏填了目标区域，或者保存文件后没有检查结果。
2. **从多条轨迹中找共同问题。** 优化器分别分析失败与成功样本：失败用于发现要补充的步骤，成功用于识别值得保留的做法。它被要求提出可推广的规则，避免把某一道题的答案写进技能。
3. **生成少量具体修改。** 修改采用追加、插入、替换、删除等操作；重复或冲突的建议先合并，再按优先级选择。本步编辑预算控制一次应用多少条修改。
4. **通过另一组任务决定是否接受。** 候选 Skill 在 selection 集上评分严格提高才被接受，持平或下降则保留旧版本。被拒绝的修改及相关失败模式会留下记录，供同一轮后续优化参考。
5. **定期回看较长期的变化。** 在 epoch 边界，用相同训练任务比较新旧技能，整理进步、退步和持续失败。慢更新补充执行模型使用的技能指导，meta skill 则帮助优化器在后续提出更合适的修改。

这套方法与本项目的联系在于：移植后出现的流程遗漏、工具使用顺序或结果检查问题，可以先收集为执行轨迹，再由优化器提出候选修订，用任务测试决定是否保留。

实验也表明反馈优化能带来效果提升。例如表1（p.7）的 GPT-5.5 表格任务中，无 Skill 为41.8，人工技能为72.9，SkillOpt为80.7。这个结果支持继续研究反馈驱动的技能修改。

### 3.3 RQ3：如何评判skill移植的成功度？

**论文采用的基本判断是：把 Skill 放到目标模型或执行环境中，让它完成独立测试任务，再用任务结果评分。** 表4的迁移实验还同时报告目标端无 Skill、使用迁移 Skill、在目标端直接优化 Skill的结果，使迁移带来的作用有明确参照。

首先，评分标准取决于任务。论文使用各基准自身的 hard success 或 exact-match 等指标：表格任务检查修改后的工作簿，问答任务按答案规则判分，ALFWorld检查任务是否完成。其共同点是尽量依据实际产物或任务状态确定成败。以上评测方式可用于设计本项目的指标。

## 4. R（Recite）

本文研究如何利用任务执行经验持续改进 Skill，并通过验证评估每次修改的实际效果。SkillOpt 将 Skill 文档作为优化对象，在保持执行模型权重不变的条件下，通过修改任务流程和操作规则改善智能体的表现。

具体而言，执行模型首先使用当前 Skill 完成一批任务，系统记录工具调用、观察结果、最终答案和任务评分。随后，优化器模型分别分析成功与失败的执行轨迹，从多个案例中识别共同问题和有效做法，并提出相应的修改建议。例如，当多次表格任务都遗漏目标区域中的空白单元格时，优化器可以补充“检查并填写完整目标范围，包括原本为空的位置”这一规则，将具体失败转化为可复用的操作经验。

由于不同案例产生的建议可能重复或相互冲突，系统会先对建议进行合并与排序，再选择本轮应用的修改。每次更新的编辑数量受到预算限制，论文将其类比为学习率。这种有界更新使相邻版本的变化相对集中，便于保留已有的有效规则，并追踪后续表现变化与修改之间的关系。

候选 Skill 生成后，需要在独立的 selection 任务集上接受评估。只有得分严格高于当前版本时，系统才接受修改；得分持平或下降时则保留原版本。被拒绝的修改及相关反馈也会被记录，供后续优化参考，以减少重复尝试无效修改的情况。因此，技能更新形成了“提出修改、执行验证、比较结果、决定是否接受”的循环。

除逐步修改外，SkillOpt 还在轮次之间进行长期回顾。系统使用相同的训练任务比较新旧 Skill，识别表现改善、出现退步、持续失败和稳定成功的情况。基于这些比较，慢更新机制将长期指导写入 Skill 的受保护区域，供执行模型使用；优化器侧的 meta skill 则总结修改经验，指导后续的建议生成与选择。两类状态分别支持任务执行和技能优化。

最终，系统导出经过验证选择的 `best_skill.md`。部署时，执行模型使用该文件即可，无需额外调用优化器。论文报告的最终技能长度约为数百至两千 token，产物较为紧凑；其生成过程仍需要多次任务执行、候选评估和优化器调用，因此训练成本需要单独考虑。

实验覆盖问答、表格、文档、数学和环境交互等任务，并在多种模型与执行框架下比较效果。在论文报告的52个已测组合中，SkillOpt 均达到最优或并列最优结果。作者还将特定模型或执行框架中优化出的 Skill 直接用于其他模型或框架，验证其迁移效果。结果表明，部分流程经验能够在目标环境中继续发挥作用，但收益随任务和目标环境而变化，其中部分表格任务的迁移提升较为明显。

本文的核心思路是将 Skill 视为可以持续修订的任务经验：从实际执行中收集反馈，提炼为具体修改，再通过独立任务验证其有效性。对本项目而言，这提供了一种可借鉴的适配流程，即记录目标环境中的执行问题，逐步调整 Skill，并使用统一的任务测试评估调整效果。

## 5. R（Review）

结合 OpenClaw Skill 向鸿蒙移植的目标，可以从这篇论文中借鉴以下三点。

**第一，将技能的通用操作步骤与各平台的工具调用方式分开整理。** 论文展示了同一份 Skill 可以在不同模型和执行框架中发挥作用，这表明这些 Skill 包含一些能够跨环境发挥作用的知识。逐 Skill 移植时，可以在移植档案中分别记录保留的操作步骤，以及需要替换的命令、依赖和工具接口。VM 路线则可以从这些案例中提取共用操作，例如将“读取表格”“写入单元格”定义为统一接口，再由 OpenClaw 和鸿蒙各自的宿主适配层调用实际工具。这样，逐 Skill 移植积累的经验也能成为设计 VM 接口的依据。

**第二，用目标端的执行反馈逐步改进适配结果。** 可以借鉴 SkillOpt 的做法，在鸿蒙端记录每次任务的工具调用、返回结果、最终产物和评分，并将失败原因对应到 Skill 说明、工具接口映射、依赖或权限等具体环节。例如，多次执行都漏填目标区域时，可以补充 Skill 中的范围检查要求；多次出现工具参数不匹配时，则可以据此调整宿主适配层的参数转换。前者可以尝试由优化器提出文本修改，后者可以形成工具适配的修复记录。每次修改后，用预留的验证任务检查效果，保留有效修改并记录被拒绝的方案。这样，方向A能够形成可追溯的调试过程，方向B也能从多个 Skill 的共同问题中发现需要统一处理的接口行为。

**第三，用同一批 Skill 和任务比较手工移植与 VM 路线。** 可以从项目计划的代表性 Skill 中建立共同测试集，明确每项任务需要生成什么产物、完成哪些功能，再在相同鸿蒙环境、目标模型和执行预算下评测两种实现。结果分别记录任务成功率、功能完成情况、运行时间和工具调用次数；适配过程则记录人工工时、修改量和后续维护工作。尤其需要将 VM 的公共运行时与宿主适配层建设成本，以及每新增一个 Skill 的适配成本分开统计，观察随着迁移数量增加，共用接口能否减少重复工作。这样既能评价单个 Skill 的移植效果，也能回答两条路线在迁移规模扩大后的成本差异。
