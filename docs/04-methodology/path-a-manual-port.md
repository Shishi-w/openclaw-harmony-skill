# 方法论文档：方向 A —— 逐 Skill 移植（传统路径）

> 目标：把 OpenClaw 的 Skill 逐个分析与改写，使其能运行在鸿蒙大模型环境。本路径**工程化、可度量**，与方向 B 提供互相验证的数据。

## 一、总体思路

一个 OpenClaw Skill 的核心是 `SKILL.md`（frontmatter + 正文）及其依赖（工具、二进制、外部服务）。移植 = **迁移指令文本 + 重绑定工具调用 + 替换底层能力**，使其适配鸿蒙宿主。

## 二、移植全过程（七个步骤）

对每个 Skill 使用 `templates/skill-port-template.md` 记录全过程：

1. **盘点（Inventory）**：列出该 Skill 的 frontmatter 字段、正文指令、依赖的工具/二进制/env/config。
2. **分类**：按 `docs/02-research/research-goals.md` 的挑战点归类（平台依赖 / 工具抽象 / 运行时 / 安全 / 规模）。
3. **适配决策**（三种情况）：
   - **直接可用**：纯提示词 Skill，无平台依赖 → 改 `os` 门控后照搬。
   - **需适配**：依赖某工具 → 找到鸿蒙等价能力（如文件→`@ohos.file.fs`、HTTP→`@ohos.net.http`），改写工具绑定与正文。
   - **不可迁移**：依赖不可能存在的二进制 → 记录原因，评估用"远程宿主"或"降级方案"替代或不支持。
4. **改写**：修改 frontmatter（去掉/替换不兼容的 `requires.bins`、`os`），重写正文中的工具调用描述使其对接鸿蒙大模型协议。
5. **对接模型**：确认鸿蒙大模型（盘古 / Harmony Intelligence）的工具调用协议与 Skill 提示词结构的兼容性。
6. **测试**：在鸿蒙模拟器/真机上运行典型输入，记录功能是否达成。
7. **归档**：写入移植档案，更新 Skill 清单。

## 三、Skill 分类清单（方向 A 组内分工依据）

建议按 A1/A2/A3 三组维护 `code/ports/` 下三个子目录，每个 Skill 一个目录：

| 分类 | 示例 Skill | 主要依赖 | 鸿蒙侧替代 |
| --- | --- | --- | --- |
| 基础系统类 (A1) | 文件读写、文本处理、数据转换 | 文件系统、命令 | `@ohos.file.fs`、ArkTS 标准库 |
| 网络/应用类 (A2) | 搜索、网页抓取、HTTP API | 浏览器、网络库 | `@ohos.net.http`、Web 组件 |
| 办公/工具链类 (A3) | 文档、表格、图像 | 第三方 CLI/二进制 | Native 库 / 降级替代 |

## 四、最容易踩的坑

1. **硬编码路径/命令**：Skill 正文里常有 shell 命令、绝对路径，鸿蒙无 shell → 逐条替换。
2. **`os` 门控**：直接写 `os: linux` 会被过滤，需删除或调整。
3. **环境变量**：`metadata.openclaw.requires.env` 的变量在鸿蒙宿主可能缺失 → 提供替代来源。
4. **模型协议差异**：OpenClaw 假设模型能理解 Markdown 指令并调用其工具；鸿蒙大模型的 Function Calling 格式若不同，需改写正文让模型输出符合鸿蒙协议。

## 五、交付物与验收

- `code/ports/` 下每个 Skill 一个目录（含改写后的 `SKILL.md` + 移植档案 + 测试记录）。
- 每完成 1 个 Skill，更新 `code/ports/README.md` 的清单表。
- 里程碑：跑通 **≥5 个代表性 Skill**，形成批量移植的经验法则，反馈给方向 B。

## 六、为方向 B 提供输入

方向 A 在移植过程中记录"哪些是共性差异、哪些是每个 Skill 都要做的同一件事"（如工具抽象、门控解析、宿主探测），这些正是 Skill VM 要抽象的部分。每周例会与 B 组对齐一次。
