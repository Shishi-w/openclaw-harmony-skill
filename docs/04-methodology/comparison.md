# 两方向对比与评测指标

> 本文档定义方向 A（手工移植）与方向 B（Skill VM）的对比维度与量化指标，作为最终实验的"成绩单"。

## 一、对比维度

| 维度 | 方向 A（手工移植） | 方向 B（Skill VM） |
| --- | --- | --- |
| 移植成本 | 每个 Skill 逐一手工改 | 一次搭 VM，之后 Skill 声明式迁移 |
| 一次性投入 | 低（即刻能跑） | 高（设计+实现 VM） |
| 批量扩展性 | 差（每加一个 Skill 都重来） | 好（新增 Skill 只要写好 IR） |
| 运行开销 | 低（无抽象层） | 可能有额外开销 |
| 维护性 | 差（平台差异散落在各 Skill） | 好（差异集中在 Adapter） |
| 对新的宿主支持 | 每个宿主重做一遍 | 加一个 Adapter 即可 |
| 可发表价值 | 低-中（工程经验） | 高（创新架构 + 实验） |

## 二、量化指标

### 移植成本指标
- **移植人时（person-hours）**：完成单个 Skill 全流程所需时间。
- **改动量**：等价代码/文本行数 diff。
- **手工干预度**：是否需要人工判断（1=纯复制，5=大量手工改造）。

### 运行效果指标
- **功能完成度**：Skill 是否达到与原装一致的功能（百分比）。
- **准确率**：在固定测试集上的成功/正确率。
- **端到端延迟**：从输入到完成的时间。
- **Token/资源开销**：VM 抽象层相对直接实现多消耗多少。

### 工程质量指标
- **可移植性评分**：同一 Skill 在新宿主上无需改动的比例。
- **维护成本**：新增 Skill / 更换宿主的改动行数。

## 三、评测数据集（建议）

- 挑选 **10 个代表性 Skill**，覆盖三类（系统类/网络类/办公类），同时纳入方向 A 与方向 B。
- 每个 Skill 准备 5-10 个典型输入用例，形成 `docs/02-research/repro/benchmark.md` 维护的评测集。

## 四、结论展示（最终报告/论文实验表）

最终用一张表格对比：`Skill | A成本 | B成本 | A完成度 | B完成度 | A延迟 | B延迟 | A可移植性 | B可移植性`，外加两组汇总统计，支撑"哪种路径适合什么场景"的结论。

## 五、公平性注意

- 方向 B 的"一次性投入"单独列出（VM 建设成本），避免与单 Skill 运行成本混淆。
- 同一测试用例、同一模型后端下评测，确保可比。
